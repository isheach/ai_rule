## 回执和恢复

- `configured` 表明入口已配置，`loaded` 需要服务或工具的实际回执，`ready` 取对应入口的就绪证据，`actually_executed` 取已观察到的调用或执行回执。字段缺证据时为 `null` 或 `unverified`。本地 broker 的 status 只涉及该调用身份及声明来源。API 协调已有的 response ID 和返回模型进入任务视图。DSH 的固定配置路线与子进程终态可核对，实际 provider、文件变更和命令结果仍需对应证据。订阅适配路径只有宿主实际调用或返回的身份记录才提供相应证据。
- DSH 的退出码 0 与终止事件 `completed` 是进程完成证据。一般任务还要有 Sol 的验收回执。受信宿主可在既有内部 `dispatch` 参数预注册只读的 `verifyExecutorReceipt`，根据冻结合同和实际回执返回带 ID 的机械检查。注册入口由宿主控制，API Sol 只接收结果。缺少相应检查时，文件或命令的证据仍以已核实宿主记录和执行者已报告内容各自标记。明确风险需要独立复核时由 Sol 界定检查并接收原回执。
- `limits.max_repairs` 可选，缺省为 `max_delegations - 1`，默认配置下是两次。在可证明为原执行后端、原会话且有已知终态时才允许修订，并继续受委派次数、响应次数、时间和用量限制。对 `unknown_after_disconnect` 或 `timed_out`，用 `get_sol_coordination` 的原协调 ID 和键读取 `recovery` 与可用的下游观察结果。旧记录也能按原键查询和重放。
- Responses 的 `store:false`、`reasoning.encrypted_content`、消息 `phase` 和工具调用回放保持原协议。较长的执行文本在给模型的直接回执中限至 12,000 UTF-8 字节并标记截断，原 journal 内已保存的执行文本仍可通过原回执读取。通过 `run` 等待前先核实宿主单次超时覆盖完整预算，需要提前返回 ID 或超时不明则用原有 `start` 和 `wait`。
